## Everything in it is our own work

| Component | Generated by |
|---|---|
| Plasma style, colour schemes, window decoration, mouse cursors, gradient surfaces | `build.py` with `tools/gen-plasma-svg.py`, `gen-aurorae.py`, `gen-cursor.py` |

**No third-party material taken over.** The theme can be redistributed
without restriction, including via the KDE Store.

## The wallpapers

Up to 0.2.5 the sentence "everything is generated programmatically" was literally true:
the backgrounds were SVG gradients from `build.py`. Since 0.2.6 there are
also 26 rendered images, and they come about differently — which is why
it is stated explicitly here.

They were rendered locally with **FLUX.1-schnell** (Apache-2.0) on our
own machine; no service, no third-party images as templates.
Then upscaled fourfold with the ESRGAN model **4x-UltraSharp** and
made seamless (offset with cross-fading for textures, mirroring for
ornaments).

Two points about the licence, so that they do not get lost:

- FLUX.1-schnell is licensed under Apache-2.0, its outputs can be used
  without restriction. Not an issue.
- 4x-UltraSharp is listed as **CC BY-NC-SA 4.0** — non-commercial.
  Whether this condition carries over to the *output* of a model is
  unresolved and judged differently. Whoever wants to be on the safe side
  re-renders the images without this step; the raw images are
  in `wallpaper/` and `tools/make-backgrounds.py` builds the packages
  from them in one run.

The gradient surfaces from `build.py` are kept — one per variant as the
package `ntlegacy-<colour-world>-flaeche`. Whoever builds from source thus
has a matching background even without the images.

## Why the icons are drawn by ourselves

The first approach was [Chicago95](https://github.com/grassmunk/Chicago95).
Its README states `License: GPL-3.0+/MIT`, but (as of August 2026,
checked twice) it has **no LICENSE file** — only a `CREDITS` with three
names. According to the same README the icons come from *Classic95*
(gnome-look.org 1012363), whose licence could not be determined. A
subproject in the same repository explicitly describes its material
as *"Screenscrapes of original assets"* from MS Office 95.

The second approach was the icon resources of
[ReactOS](https://github.com/reactos/reactos) — GPL-2.0 and developed
clean-room, so beyond reproach. Two reasons spoke against it in the end:

1. **Looks.** The ReactOS icons are more modern than NT 4.0: blue folders
   with gradients instead of yellow surfaces. The 4-bit layers of the
   `.ico` files would be more classic, but are unusable throughout because of
   dithering artefacts.
2. **Coverage.** Toolbar icons — copy, paste, back,
   view modes — exist there as bitmap strips in program resources
   or not at all. They would have had to be drawn anyway.

If half of it is created by ourselves anyway, it is more consistent to draw
everything ourselves: a uniform style, one licence, no third-party source to maintain.

## The icon set

```bash
tools/gen-icons.py nt-legacy/icons-nt/NTLegacyIcons
tools/gen-icon-aliases.py     nt-legacy/icons-nt/NTLegacyIcons
tools/gen-symbolic-aliases.py nt-legacy/icons-nt/NTLegacyIcons
```

162 drawn icons in 16/22/32/48 px, plus links for further
names. Of the names that Dolphin and PCManFM-Qt request, none
falls back to Breeze any more.

Since 0.2.7 in eight sizes: 16, 22, 32, 48, 64, 96, 128 and 256 px — all
the ones Dolphin offers in its zoom slider.

The road there is worth a lesson. In 0.2.6 the same drawing lay there instead
as an SVG under `scalable/`, valid from 64 px; according to the
freedesktop specification it should win from that size on, and measured
with `QIcon` it did. For the reporter it still stayed
pixelated.

Reproduced and measured: at 200 px Dolphin reads
`places/48/folder.png` and scales it up — the SVG is not even
opened. KDE programs load icons via **KIconLoader**, not via
Qt's own loader, and that one does not consult `scalable` directories
here. Hence real bitmaps in every size now: that does not depend on any
weighting.

The SVGs under `scalable/` stay where they are — pure Qt programs without
KDE integration find them, and they cost little.

It was measured without `strace`: backdate the access times of the icon files with
`touch -a -d "3 days ago"`, then start the program and
check which file has a new date. `relatime` does not update anything
younger than 24 hours by itself — that is where the first
measurement attempt had failed.

The object colours deliberately do **not** follow the colour scheme: under
Windows NT the folder stayed yellow and the drive grey, no matter which
colour world was set. Only the line and accent colours follow
the variant.

## SE98 — checked, not taken over for the same reason

`fetch-icons.sh` can now also fetch [SE98](https://www.opencode.net/nestoris/Win98SE).
The set is tempting: around 6,400 names against our 229, in
sizes from 8 to 1024 px, with an `index.theme` that lists all 109
directories completely — much better maintained than
Chicago95. Of the icon names that Plasma actually requests on this system
and that we lack, it covers 93.

It is still **not** in the repository, for the same reason
as Chicago95 — only the finding is clearer here. Unlike Chicago95
it comes with a `LICENSE`, the full text of GPL-2.0. But the project's own README
describes what lies underneath:

> "Enhanced Classic icon theme […] **from MicroSoft Memphis project** […]
> inspired by Chicago95 theme (**actually it's a manual copy-paste
> fork**) of Grassmunk"

> "there are some icons from **Faenza** and **Chicago95** themes in it"

"Memphis" was the development name of Windows 98. With Chicago95 the
origin of the bitmaps was *unresolved*; here it is stated plainly. A
licence only covers what the person applying it created — nobody can put the GPL
on someone else's bitmaps. On top of that: there is no
`CREDITS` and no per-file attribution, so the self-drawn part
cannot be separated from the adopted one at all.

For your own machine that does not matter, for redistribution it does.
Hence the same procedure as with Chicago95: can be fetched, not
shipped.

What we take from it instead is the gap list.
`tools/missing-icons.py` determines which names the system requests
and our set does not have — from the `.desktop` files and the
strings of the KF6 libraries, filtered against Breeze. With
`--compare` it also shows whether SE98 would have a template:

```bash
tools/missing-icons.py nt-legacy/icons-nt/NTLegacyIcons \
    --compare nt-legacy/icons/NTLegacySE98
```

That is the permissible use of a third-party set: look, then
draw it yourself.

## The third-party sets remain usable

`fetch-icons.sh` installs Chicago95 as `NTLegacy` and SE98 as
`NTLegacySE98`. Neither is in the repository (`nt-legacy/icons/`
is in `.gitignore`) and neither is part of redistribution — whoever has
fetched them can select them in System Settings.

## Not included

Fonts. The theme ships none; it uses what the system provides.
